# Routes and permissions

The route table below maps each public operation to the permission and signed request profile it uses, and says whether Anis signs its answers. Every machine request is signed; only the answers marked signed are verified, and on those routes every answer, success and refusal, is signed — one without a signature is refused as `signature_missing`. Read permissions and order permissions are evaluated for each call.

The gateway publishes 42 routes; this SDK supports 39. `GET /v1/application/networks`, `POST /v1/application/networks` and `POST /v1/application/networks/remove` are permanently excluded from the SDK. **Staging only — testing endpoints, not available in production.** **بيئة الاختبار فقط — نقاط نهاية للاختبار، غير متاحة في الإنتاج.**

New product page methods return `ProductPage<T>` and preserve an explicit `nextCursor: null`; null or an absent cursor ends iteration. Existing catalogue page signatures retain `Page<T>`.

The full published route and error contracts are checked against the SDK's route table in the contract drift tests. For a request to be considered, Anis first validates its signature, then checks the required permission, source network, and resource access. A permission authorizes a capability; it does not override wallet grants, account state, purchase limits, or business rules. Lists count as read calls for the route's permission. `list()` follows continuation cursors; use a `listPage({ cursor, signal })` method when the application needs to control page boundaries. Pass a returned cursor back exactly as received; omit `cursor` for the first page and pass `signal` to cancel the request.

Meter and direct recharge permissions come in read and create pairs: `meter_charges:read`, `meter_charges:create`, `direct_recharges:read` and `direct_recharges:create`. A create permission includes the reads of its own product (packages, charges, products, locations, quotes and operation reads), but a read permission never allows a create. Reading an operation by id, correcting a recipient and the webhook routes act on this application's own operations and endpoint, so they carry no wallet in the path. The webhook self-service routes need no permission, only an admitted application identity and source network.

Every Partner API route counts toward `requests`. Meter and direct recharge creates count toward `orders` and, like card orders, against the application's shared daily spending cap. Orders also count toward `orders`; card and invoice reveals also count toward `reveals`. Enrollment requests and the public signing-key document are outside those usage counters.

## Before Anis evaluates the business request

Anis validates request shape, signature and body digest, credential state and freshness, nonce freshness, rate limits, source network, permission, and wallet grant before making an order decision. The order of these checks is not part of the contract, so do not rely on which refusal appears first. Network or permission refusals use `insufficient_scope`; wallet access uses `wallet_not_granted`. The signature self-check reports what Anis received when a proxy or local request builder may have changed the signed values.

Access stops require no scope for an admitted request. They sign method, authority, path, query, content-digest, nonce, and x-anis-date, including the digest of the JSON reason body; they do not send an idempotency key. Suspension requires staff to resume; revoked keys need a new enrollment.

Recipient PATCH answers only signed HTTP 202 with the three-member processing acknowledgement and a Location for the matching direct recharge read. `updateRecipient` returns `DirectRechargeProcessing`, the same type a 202 create answers, with the acknowledgement in `accepted` and the verified `location`; read that operation or wait for its webhook to observe the correction. An exchange body is not returned by PATCH.
